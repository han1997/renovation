# 项目开发约定

> 装修管家项目的全局开发约定。本文件为项目级规范，优先级高于各分层规范（frontend / backend）。

---

## 一、语言约定

项目所有产出物统一使用**中文**：

- 文档（README、spec、PRD、设计说明）
- 代码注释（仅在必要处添加，能自解释的代码不写注释）
- Git 提交信息（commit message）
- AI 助手与用户的所有沟通

> 说明：`.trellis/spec/frontend/index.md` 与 `.trellis/spec/backend/index.md` 中原有「All documentation should be written in English」的约定已废弃，统一改为中文。

---

## 二、Git 提交信息格式

提交信息采用「中文类型前缀 + 中文描述」格式：

```
<类型>: <中文描述>
```

### 类型清单

| 前缀 | 用途 | 示例 |
|------|------|------|
| `新增` | 新功能 | `新增: 首次设置向导，支持面积/档次选择` |
| `修复` | 问题修复 | `修复: 预算超支金额计算错误` |
| `文档` | 文档变更 | `文档: 补充 README 使用说明` |
| `重构` | 代码结构调整，不改外部行为 | `重构: 拆分预算页渲染逻辑` |
| `配置` | 构建 / 配置 / 基础设施 | `配置: 初始化 Git 仓库` |
| `性能` | 性能优化 | `性能: 首页渲染减少重复 DOM 查询` |
| `测试` | 测试相关 | `测试: 补充知识库数据完整性校验` |

### 写作要求

- 标题行简要描述「改了什么」，不超过 50 字
- 必要时标题后空一行，附详细说明（为什么改、影响范围、注意事项）
- 一条提交只做一件事，避免混合多个无关改动

示例：

```
新增: 首次设置向导，支持面积/档次选择

三步问卷收集面积、城市、装修方式与预算，自动生成预算分类。
向导数据写入 Store.state.profile，可在「我的」页重新进入修改。
```

---

## 三、更新日志

本项目**不维护单独的 CHANGELOG.md 文件**，以 git 提交历史作为更新记录：

```
git log --oneline
```

因此：**提交信息的质量即更新日志的质量**。每条提交都应清晰说明改了什么、为什么，让人无需读代码就能了解变更内容。

---

## 四、分支约定（建议）

- `main`：主干，保持可用状态
- `feat-<功能名>`：功能开发分支，完成后合并回 `main`
- `fix-<问题名>`：问题修复分支

小型项目可灵活处理，不强制使用分支策略，但提交前请确认改动不会破坏现有功能。

---

## 五、README 维护

`README.md` 是项目的入口文档，发生以下变更时应同步更新对应章节：

- 新增或下线功能 → 更新「功能概览」
- 使用方式变化 → 更新「使用方法」
- 目录结构调整 → 更新「项目结构」
- 新增外部依赖或工具 → 更新「技术说明」

---

## 六、忽略规则

- 根目录 `.gitignore` 忽略操作系统文件、编辑器临时文件、Python 缓存等
- `.trellis/.gitignore` 忽略 Trellis 运行时文件（`.runtime/`、`.session-id`、`.developer` 等），git 会自动合并两级忽略规则
- `.trellis/` 项目配置（spec / tasks）、`.trellis/workspace/` 开发日志均应提交

---

## 七、AI 执行纪律（硬性约束，违反即事故）

> 本节由真实事故沉淀（2026-09-05，流程页 UI 优化任务）：AI 在调研 Web 版 CSS 时，同一条 `Select-String` 查询命令无变化地重复执行了 50+ 次，每次结果相同却不做判断继续循环，消耗大量时间且零产出，用户被迫中断。以下规则为**永久生效的硬性约束**。

### 禁止：无进展的重复工具调用（Tool Loop）

**定义**：连续 2 次执行语义相同（命令相同或仅参数微调）的查询/命令，且上一次结果未产生新信息或新决策，即构成循环。

**硬性规则**：

1. **同一查询最多执行 2 次**。第 2 次仍无新信息 → 必须停止，换方法或换问题。
2. **每次工具调用前自问**：「这次调用的结果会改变我下一步做什么吗？」答案为否 → 不调用。
3. **连续 3 次工具调用未产出任何决策或代码变更** → 强制停下，向用户汇报当前卡点，请求方向确认。
4. **禁止用重复查询「确认已知结果」**：已经读到过的内容不因再查一次而更可信。

**正确做法**（Wrong vs Correct）：

```text
# Wrong —— 结果相同仍无限重复
Select-String "pattern" file.css   # 结果: A
Select-String "pattern" file.css   # 结果: A（相同）
Select-String "pattern" file.css   # 结果: A（相同）……×50

# Correct —— 第 2 次无新信息即停止，改用一次性读取
Select-String "pattern" file.css   # 结果: A，发现需要更多上下文
Get-Content file.css               # 一次性读全文件，基于完整内容做决策
```

### 调研产出纪律

- 调研的目的是**支撑决策**：每次调研后必须落到「方案 / 代码 / PRD 更新」三者之一。
- 信息已足够时立即动手实现，不为「更保险」继续收集。
- 用户表达不耐烦（如「弄这么久」「一个成果都没有」）时，最高优先级是**交付可见成果**，暂停一切非必要调研。

### 适用范围

本节约束所有 AI 会话（主会话与 sub-agent），不因任务大小、流程状态（planning / in_progress）而豁免。
